Publish once, serve everywhere

A single structured description of each government service, published automatically to every channel — web, API, AI agent, catalogue, and print.

The maintenance problem

The problem isn’t building services — it’s maintaining them across channels.

Today, a single government service like Apply for Universal Credit exists as multiple parallel descriptions, each maintained by a different team:

  • A GOV.UK web page (content team maintains)
  • PDF and paper forms (forms team maintains)
  • Phone script guidance (contact centre maintains)
  • Internal caseworker guidance (operations team maintains)
  • API documentation (technology team maintains, if it exists)

When eligibility rules change, five teams update five artefacts. They drift. Citizens get different answers depending on the channel. Now add AI agents as a sixth channel, and the problem compounds.

The question is not whether departments should support AI agents. It is whether they can afford to maintain yet another parallel description of each service — or whether this is the moment to describe services once and publish everywhere.

3

What ‘describe once’ means

Five structured artefact types capture everything needed to deliver a service on any channel.

Manifest

What the service is: name, department, eligibility summary, data it needs, SLA, complaint routes, escalation contacts. The service’s identity card.

Policy ruleset

Who is eligible and why: machine-readable rules with human-readable failure reasons. “You must be over 16”, “You must have a valid driving licence”. Edge cases documented.

State model

What the journey looks like: a step-by-step map from “not started” to “completed”. Which steps are required, which are optional, what unlocks what. The service’s choreography.

Consent model

What data is shared and why: every piece of data the service needs, who it comes from, what it’s used for, how long it’s kept, and how to revoke. The service’s data contract.

Card definitions

What the citizen sees: the actual form fields, their types, validation rules, conditional visibility, and pre-fill sources. The service’s user interface as data.

These five artefacts are already defined and working. The Legibility Studio generates them today for AI agents. The ‘publish once’ model extends the same artefacts to every channel.

How this aligns with GDS standards

Publish once is not a departure from existing government digital standards. It is a direct implementation of them.

Point 3: Joined-up channels

Publish once inherently delivers a consistent experience across every channel. One source of truth means citizens get the same answer whether they use the web form, the AI agent, or the phone script generated from the same description.

Point 13: Open standards

Service artefacts are JSON, output includes OpenAPI 3.0, Schema.org, DCAT. Every format is machine-readable and standards-based.

Technology Code of Practice: share, reuse, collaborate

The generator layer is reusable across all departments. Build once, use 1,544 times.

API Technical Standards

OpenAPI 3.0 is the government-mandated format. The publish-once platform generates compliant specs automatically from service descriptions.

International context

Three countries have demonstrated, at national scale, that government services are data — not websites.

Estonia — X-Road

929 institutions. 3,000+ digital services. Two decades of secure, decentralised data exchange. X-Road proved that government services can be described as interoperable, machine-readable specifications and federated across organisations. The UK’s publish-once model builds the service description layer that X-Road’s infrastructure was designed to carry.

Singapore — SGTS

The Singapore Government Tech Stack provides composable modules — identity, payments, notifications — assembled into services. MyInfo’s deployment time dropped from one year to four months. SGTS proves that “describe once, compose everywhere” works at national scale. The publish-once model applies the same principle to the UK’s service artefacts.

Ukraine — Diia and the Agentic State

23 million users. 130+ services. Diia.AI — the world’s first government AI agent delivering real services via MCP — launched September 2025. Built under active wartime conditions using a hybrid architecture (on-premise data sovereignty + cloud AI). Ukraine’s Ministry of Digital Transformation coined the term “Agentic State”: citizens express intent, AI executes the required processes. The UK has signed a trilateral cooperation agreement with Ukraine and Estonia on e-governance and AI.

Three countries, three architectures, one convergent insight: government services are data, not websites. Describe them as structured specifications, and every delivery channel — including AI agents — becomes a rendering target.

8

What departments need to do

Three steps. The first two are already supported by tooling. The third is the publish-once extension.

Step 1
Describe

Use the Legibility Studio to describe each service: select an interaction type, fill in the manifest (name, eligibility, SLA, complaints), define policy rules, map the state model, specify consent requirements, and define the card fields citizens will see.

Step 2
Review

The studio shows gap analysis: which artefacts are complete, which are missing fields, what coverage looks like across the department. AI-assisted generation can draft artefacts from existing GOV.UK content — departments review and refine.

Step 3
Publish

Select output channels and publish. The platform generates channel-specific outputs, stores immutable versions, and tracks what was published where. When something changes, update the description and re-publish — all channels update together.

9

What this makes possible

Describing services as data is not the end state. It is the precondition for three capabilities that are currently impossible.

Proactive services — if a citizen’s circumstances change (recorded through one service), the platform can identify other services they’re now eligible for and notify them automatically. Today this requires manual cross-referencing between departments.

Life event orchestration — 16 life events have been mapped across all 1,544 services. When a citizen experiences a birth, bereavement, job loss, or retirement, the platform identifies all relevant services and sequences them. This is not possible when each service exists in isolation.

Departmental analytics — when services are described as data, departments can measure coverage, identify gaps, compare interaction patterns, and understand where citizens get stuck. The evidence plane already captures every agent interaction — publish-once makes that evidence actionable across channels.

Publishing once is not a technical convenience. It is the precondition for joined-up government. As long as each service exists as separate, channel-specific descriptions, joining them up requires heroic manual effort. When services are data, joining them up is computation.
