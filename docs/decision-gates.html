decision gates

structured routing questions at the boundary between probabilistic and deterministic layers

the problem

when a citizen says "my husband died three weeks ago and I don't know what to do," the system needs to ask routing questions — have you registered the death? did they leave a will? — before it can determine which services to surface and in what order.

these questions have a small number of finite options. each answer has deterministic consequences on the journey. but the conversational moment when the question should be asked is probabilistic — only the LLM can judge the right time.

without decision gates, the LLM asks these questions as plain text, expecting the citizen to type a free-form response. in a bereavement scenario, this means asking a grieving person to formulate words when they could simply tap a button.

what decision gates are

a decision gate is a structured routing question with tappable options that sits at the boundary between the LLM and the state machine. it has three characteristics that distinguish it from other primitives in the stack:

  • data-defined — the question, options, and routing effects are specified in JSON, not generated by the LLM
  • LLM-signalled — the LLM decides when to surface a gate by emitting a gate ID in its structured output
  • deterministically resolved — each option maps to routing effects (enable services, skip services, set facts) that are applied immediately

the LLM decides when. the data defines what. the system enforces what happens next. each layer stays in its lane.

how gates differ from other primitives

primitive purpose who defines it who triggers it
cards collect data fields for a service in progress card registry (state × interaction type) state machine transition
consent permission to share data service consent model state machine (eligibility-checked)
decision gates route the journey based on citizen's situation life event or service gate data LLM (recognises conversational moment)
tasks actionable next steps for the citizen LLM + deterministic injection LLM (per response)

the flow

gate definitions (JSON) → loaded into registry at request time
  ↓
orchestrator prompt includes available gate IDs + descriptions
  ↓
LLM recognises routing moment → emits decisionGateId in structured output
  ↓
chat route resolves gate definition from registry
  ↓
client receives gateRequests[] → renders DecisionGateCard
  ↓
citizen taps an option → confirms
  ↓
summary message flows back to chat (as if the citizen typed their choice)
  ↓
routing effects applied: enableServices / skipServices / setFacts

gate definition format

gate definitions live in data/decision-gates/{life-event-id}.json for life-event-level gates, or data/services/{slug}/decision-gates.json for service-level gates.

{
  "lifeEventId": "bereavement",
  "gates": [
    {
      "id": "bereavement-death-registered",
      "question": "have you been able to register the death yet?",
      "helpText": "in England and Wales, a death must usually be registered within 5 days.",
      "sensitive": true,
      "options": [
        {
          "value": "yes",
          "label": "yes, I've registered the death",
          "consequence": "that's one important step already done.",
          "routingEffect": {
            "skipServices": ["gro-register-death"],
            "enableServices": ["dwp-tell-us-once", "dwp-bereavement-support"],
            "setFacts": { "death_registered": "yes" }
          }
        },
        {
          "value": "no",
          "label": "no, not yet",
          "consequence": "that's usually the first step, and I can help you with it.",
          "routingEffect": {
            "enableServices": ["gro-register-death"],
            "setFacts": { "death_registered": "no" }
          }
        },
        {
          "value": "not-sure",
          "label": "I'm not sure what that involves",
          "routingEffect": {
            "setFacts": { "death_registered": "unknown" }
          }
        }
      ]
    }
  ]
}

routing effects

each option can specify three types of deterministic consequence:

  • enableServices — make services available in the active plan that were previously gated
  • skipServices — remove services from the plan entirely (citizen has already done them, or they're not relevant)
  • setFacts — inject key-value pairs into the orchestrator's fact context, available to all subsequent turns

who owns gate definitions

in a live platform, gate ownership follows two patterns:

  • service-level gates — owned by the department. published through the legibility studio alongside the service manifest, state model, and consent model. the department knows its own eligibility questions.
  • life-event-level gates — curated centrally. these route across multiple departments' services, so no single department owns them. in production, they would live in the service graph or a central registry maintained by the platform team.

in the prototype, gate definitions are static JSON files — the same pattern used for all service artefacts. the resolution chain is designed with two tiers (static files + database overrides) so it maps cleanly to the production publishing pipeline.

the boundary negotiation

decision gates are an example of a broader pattern in the stack: negotiating the boundary between what the LLM should decide and what the system should enforce.

the LLM is good at recognising conversational moments — it can tell when a bereaved person is ready to be asked a practical question, and it can wrap that question in appropriate empathy. the system is good at knowing what the options are and what should happen based on each answer.

gates formalise this division. the LLM provides the framing. the data provides the structure. the system provides the consequences. neither layer reaches into the other's domain.

this is the same principle that governs consent (the system presents the grants, the citizen decides, the LLM acknowledges) and state transitions (the LLM proposes, the state machine validates). decision gates extend the pattern to routing questions that don't fit neatly into either the card system or the state machine.
