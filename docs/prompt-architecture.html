Platform Briefing

Prompt Architecture

Two apps, two philosophies, one platform. How citizen-02 and citizen-03 prompt differently — and what that means for control, legibility, and agent autonomy.

citizen-02 builds a detailed, layered system prompt and relegates the LLM to narration. citizen-03 gives the LLM tools and a short brief, then lets it reason. Both reach Claude through the same AnthropicAdapter, but the prompts they send could not be more different.

Two prompt philosophies

The same platform supports fundamentally different approaches to LLM agency. The prompt is the lever.

citizen-02 — Orchestrator Model

"Platform decides, LLM narrates"

The orchestrator runs a 15-step deterministic pipeline. It evaluates policy, manages state, builds field collectors, and injects per-state instructions. The LLM receives a 3,000–5,000 token system prompt that tells it exactly what to do in the current state, what NOT to say, and which state transition to fire.

The LLM's job: Generate citizen-facing text and propose (not decide) state transitions. The platform validates everything after.

packages/runtime/src/orchestrator.ts

citizen-03 — Thin Agent Loop

"LLM reasons with tools, platform validates"

The API route loads persona data, builds an ~800-token system prompt, and hands the LLM 6 tools. The LLM runs in a loop (max 8 iterations), deciding which services to explore, when to check eligibility, and how to guide the citizen. The platform executes tool calls and returns results.

The LLM's job: Decide strategy, call tools, synthesise results into cards and quick replies.

apps/citizen-03/app/api/chat/route.ts

Same adapter, different prompts. Both apps import AnthropicAdapter from @als/adapters and call execute({ systemPrompt, messages, tools? }). The difference is entirely in what systemPrompt contains and whether tools is populated.

citizen-02: The Orchestrator Model

The platform does the thinking. The LLM does the talking. Every decision about which service, which state, which data to collect, and which guardrails to apply is made in deterministic code before the LLM is called.

The 15-step pipeline

Each request flows through this pipeline. Steps 1–6 and 8–15 are deterministic. Only step 7 touches the LLM.

  1. Policy evaluation deterministic
    Evaluate eligibility rules against persona data using PolicyEvaluator
  2. State machine setup deterministic
    Initialise StateMachine from state-model.json, set current state
  3. Field collector deterministic
    Build FieldCollector from manifest input schema, seed with known persona data
  4. Agent selection deterministic
    Pick "triage" (no active service) or "journey" (service in progress)
  5. Strategy context deterministic
    Build service context via the pluggable ServiceStrategy
  6. System prompt assembly deterministic
    buildTriagePrompt() or buildJourneyPrompt() — composes 6 layers
  7. LLM generation ai
    Send assembled prompt + message history to Claude. Agentic loop with optional tool calls.
  8. Parse structured output deterministic
    Extract JSON block (title, tasks, stateTransition, extractedFacts) from response
  9. Build tasks deterministic
    Map parsed tasks to typed TaskEntry objects
  10. State transition validation deterministic
    Validate LLM's proposed transition, apply forced transitions, match auto-transition patterns
  11. Deterministic task injection deterministic
    Override LLM tasks with platform-generated housing/bank cards at specific states
  12. Consent resolution deterministic
    Surface consent grant cards at eligibility-checked state
  13. Handoff detection deterministic
    Check for escalation triggers (edge cases, user distress)
  14. Record extracted fields deterministic
    Feed LLM-extracted facts into FieldCollector
  15. Version metadata platform
    Hash the prompt, stamp ruleset + state model versions for audit trail
Notice: The LLM runs at step 7 out of 15. Everything before it is setup; everything after it is validation and override. The platform has the final word on state transitions, tasks, and consent.

The 6 layers of a citizen-02 system prompt

Assembled by buildTriagePrompt() or buildJourneyPrompt(), concatenated with --- separators.

Layer 1 — Agent Personality

Who is the agent?

Static text files. DOT (cautious, asks permission, formal tone) or MAX (proactive, auto-fills, friendly tone). Same artefacts, different behaviour.

apps/citizen-02/data/prompts/dot-system.txt · max-system.txt

Layer 2 — Persona Style

How should the agent communicate?

Text files per citizen persona — communication preferences and background. Loaded by persona ID.

data/prompts/persona-emma-liam.txt · persona-margaret.txt · etc.

Layer 3 — Scenario Context

What service domain are we in?

Detailed background on the service: eligibility criteria, process steps, key info needed. Static files or generated from manifests via generateScenarioPrompt().

data/prompts/scenario-benefits.txt · scenario-driving.txt · etc.

Layer 4 — Service Artefacts

What are the rules, states, and consent requirements?

Machine-readable JSON: policy.json (eligibility rules), state-model.json (state machine), consent.json (data-sharing grants). Injected as structured context.

data/services/apply-universal-credit/policy.json · state-model.json · consent.json

Layer 5 — State Instructions

What should the agent do in this state?

Per-state guidance: what to do, what to avoid, which transition to fire. Hand-crafted JSON for core services; template-generated for 100+ graph-only services.

data/services/*/state-instructions.json · packages/schemas/src/state-instruction-templates.ts

Layer 6 — Output Format & Guardrails

How should the agent structure its response?

Reusable constants: STRUCTURED_OUTPUT_INSTRUCTIONS, TASK_INSTRUCTIONS, FACT_EXTRACTION_INSTRUCTIONS, ACCURACY_GUARDRAILS, TITLE_INSTRUCTIONS.

packages/runtime/src/prompt-fragments.ts

State instructions: the per-step playbook

The most detailed and controlling part of a citizen-02 prompt. Each state gets a multi-paragraph instruction with explicit DO and DO NOT rules.

Hand-crafted (4 services)

Service-specific JSON

Per-state instruction strings, plus forcedTransitions (automatic state skips) and autoTransitions (regex patterns that match user messages to trigger transitions).

data/services/{slug}/state-instructions.json

Template-generated (100+ services)

Interaction type templates

Four templates — APPLICATION, LICENSE, REGISTER, PORTAL — with placeholders ({serviceName}, {department}, {eligibilitySummary}) resolved at runtime from graph node data.

packages/schemas/src/state-instruction-templates.ts

state-instructions.json — "eligibility-checked" state 
Eligibility has already been checked and results were presented.
The citizen is now reviewing consent cards that appeared below your previous message.

If the citizen's message contains consent decisions (granted/denied) OR indicates
agreement to proceed (e.g. "yes", "go ahead", "I consent", "proceed"):
  - Acknowledge their consent, thank them
  - Present their personal details for confirmation using ACTUAL data from the
    DATA ON FILE section: full name, DOB, NI number, address
  - Ask "Does everything look correct?"
  - Set "stateTransition" to "grant-consent" in the JSON block

If the citizen asks a question or provides other information:
  - Answer their question helpfully
  - Gently remind them to review and approve the consent cards below
  - Do NOT set a stateTransition

Do NOT re-explain eligibility — it's already done.
Do NOT mention identity verification — it's already done.
Do NOT discuss housing, bank details, income, or any later steps yet.
Do NOT include any tasks in the JSON block.
Control pattern: Every state instruction has explicit DO and DO NOT rules, specifies exactly which stateTransition to fire, and prevents the LLM from discussing future steps. Even after all this, the platform still validates the proposed transition at step 10.

A fully assembled prompt, approximately structured like this:

---

---
PERSONAL DATA EXTRACTION: When the user reveals personal facts... (~100 tokens — fact extraction)
---

INSTRUCTIONS FOR THIS STATE: Eligibility has been checked... (~250 tokens — state instructions)

CONSENT REQUIREMENTS: share-ni-number: Share NI... (~80 tokens — consent)
---
FIELD COLLECTOR: Required: [...], Collected: [...] (~60 tokens — field status)
---
Remember: Stay in character as DOT agent... (~30 tokens)
ACCURACY GUARDRAILS — CRITICAL: Do NOT fabricate... (~100 tokens)
ACTIONABLE TASKS: When your response contains... (~500 tokens — task format)
STRUCTURED OUTPUT FORMAT — CRITICAL: At the END of every response... (~250 tokens — output format)

citizen-03: The Thin Agent Loop

Give the LLM tools and a short brief. Let it reason about what to do. The platform executes tool calls and validates results, but the strategy is the LLM's.

The agent loop

A simple while loop, max 8 iterations. No state machine, no policy evaluator, no field collector in the loop itself.

  1. Load context platform
    Load persona data, initialise adapter and artefact store
  2. Build system prompt deterministic
    ~800 tokens: role, response format (cards + quick replies), tool usage guidelines, citizen profile
  3. Attach 6 tools platform
    Tool definitions from @als/agent-tools passed as Anthropic tool_use specs
  4. LLM decides + calls tools ai loop
    LLM reasons, calls tools, gets results, calls more tools, until it has a final answer
  5. Parse cards + quick replies deterministic
    Extract JSON block from response, separate display text from structured data
  6. Generate title ai (optional)
    Separate single-turn LLM call for conversation title
Notice: The LLM runs at step 4 and may iterate up to 8 times. There is no platform-side policy evaluation, state management, or task injection. The LLM uses tools to do these things itself.

The 6 tools the LLM gets

Defined in packages/agent-tools/src/tool-definitions.ts. These are Anthropic tool_use definitions passed alongside the system prompt.

Tool What it does LLM decides
query_service_graph Search 108 services by life event, department, type, or keyword Which filters to use, how many queries to make
get_life_event_plan Get topologically-ordered service plan for a life event When to call it, which life event matches the citizen's situation
get_related_services Get REQUIRES/ENABLES edges for a service Which service to explore, whether to follow the dependency chain
check_eligibility Evaluate policy rules against citizen data When to check, what citizen data to pass
get_citizen_context Retrieve citizen's data profile (verified, submitted, inferred tiers) Whether to load context at conversation start
record_evidence Record a trace event in the append-only evidence store What events to record, when to create audit trail entries

What the LLM actually receives

The entire system prompt. Not an excerpt — this is the real thing.

citizen-03 system prompt (complete) 
You are a UK government services assistant helping Margaret Evans.

## Your Role
You help citizens navigate UK government services one step at a time. You have tools to search services, check eligibility, and understand service relationships.

## CRITICAL: Response Format
Your response MUST be SHORT — 2-4 sentences of conversational text, maximum. Do NOT list every service. Do NOT write walls of text.

After your short text response, you MUST include a structured JSON block that provides interactive cards and suggested next actions. The UI renders these as tappable cards.

```json
{
  "cards": [
    { "type": "service", "id": "...", "title": "...", "urgency": "immediate" | "soon" | "later", "eligible": true | false | null },
    { "type": "action", "title": "...", "description": "..." },
    { "type": "info", "title": "...", "description": "..." }
  ],
  "quickReplies": ["...", "...", "..."]
}
```

## Guidelines for cards
- Show 2-4 cards maximum, not every service you found
- Prioritise by urgency: what MUST they do first?
- For a life event with many services, show the FIRST STEP only

## How to Work
1. Use `get_citizen_context` to understand their situation
2. Use `get_life_event_plan` or `query_service_graph` to find services
3. Use `check_eligibility` before saying someone qualifies
4. Guide them ONE STEP AT A TIME — don't overwhelm

## Constraints
- Never fabricate service information
- Check eligibility before claiming someone qualifies
- If unsure, say so

## Citizen Profile
Name: Margaret Evans
Location: Brighton, BN1 4GH
That's it. Compare this to citizen-02's ~3,000–5,000 tokens. No state machine, no per-state instructions, no accuracy guardrails, no task format, no fact extraction. The LLM figures out what to do by calling tools.

Streaming variant

citizen-03 also has a streaming endpoint (/api/chat/stream) that uses SSE to push tool progress events in real-time:

tool_start

Fired when the LLM calls a tool. Includes a human-readable label like "Searching services" or "Checking eligibility".

tool_complete

Fired when a tool returns. Includes a summarised output (not the full result) and duration in ms.

reasoning

Streams the agent's internal reasoning text between tool iterations.

response

Final event with the complete response: text, cards, quick replies, tool log, title.

Side-by-side comparison

The same question — "I've just lost my job, what benefits can I get?" — produces very different internal flows.

Dimension citizen-02 citizen-03

Tools Optional, strategy-dependent (MCP tools or inline JSON) Always — 6 tools from @als/agent-tools
LLM loop iterations Max 5 (tool use only) Max 8 (tool use is the primary mechanism)

Neither is "better". citizen-02 maximises platform control and auditability — ideal for high-stakes benefit applications where the platform must guarantee correctness. citizen-03 maximises agent flexibility — ideal for exploratory conversations where the citizen's needs aren't yet clear.

Single entry point for all LLM calls. Both apps call execute({ systemPrompt, messages, tools? }). The adapter handles API key management, request formatting, and response parsing.

Prompt design principles

Patterns that emerge from looking at both approaches together.

Control is a spectrum

citizen-02 maximises platform control. citizen-03 maximises agent autonomy. The same service data powers both. The prompt is the dial.

Guardrails scale with stakes

citizen-02 adds ACCURACY_GUARDRAILS, per-state DO NOT rules, and post-LLM validation for benefit applications. citizen-03's guardrails are four bullet points — sufficient for exploratory navigation.

Tools replace prompt layers

citizen-02 injects policy results and state context into the prompt. citizen-03 gives the LLM tools to fetch these itself. Same information, different delivery mechanism.

Personality is a layer, not a fork

citizen-02 proves that swapping 300 tokens of Layer 1 produces fundamentally different agent behaviour. citizen-03 doesn't have this layer yet — it's a design space waiting to be explored.

Composition over monolith

citizen-02 composes from 6 layers, 5 fragments, and per-state instructions. No single file contains a complete prompt. This enables the same fragments to serve different agent modes.

Audit via architecture

citizen-02 stamps every response with a prompt hash and version metadata. citizen-03 logs every tool call with timing and I/O. Both create an audit trail, but by different means.
