Application Guide

Legibility Studio

The admin platform where service designers author, audit, and manage the artefacts that make government services legible to AI agents.

For an AI agent to act on a citizen's behalf it needs more than an API — it needs to understand what a service does, what it requires, what policy governs it, and how consent is managed. Legibility Studio is where departments publish that understanding as structured, machine-readable artefacts.

Service catalogue

The catalogue holds every government service the system knows about. Services come from two sources and are classified into eight typologies.

Two source types

Full services

Hand-authored artefact sets in data/services/*/

  • Complete manifest, policy, state model, and consent files
  • Used in live demos and agent orchestration
  • Editable through the Studio form editor
  • Actions: detail view, edit, view ledger, delete

Catalogue services

Imported from the GOV.UK service graph

  • Basic metadata only — name, department, life event mapping
  • Can be promoted to full services
  • LLM generation can scaffold artefacts automatically
  • Represents the long tail of government services

Eight service typologies

Every service is classified by interaction pattern. The typology dashboard on the services page shows a collapsible summary of distribution across all eight types, helping designers identify under-served categories.

benefit · entitlement · obligation · registration · application · document · legal_process · grant

Filtering and search

The services table supports filtering by source (full / catalogue / all), typology, department, life event, and free-text search. Services are split into two sections: promoted Agent Services (highlighted) and the full GOV Services table.

4

The artefact model

Each full service is defined by four artefact types stored as JSON files. Together they give an AI agent everything it needs to execute a service on a citizen's behalf — deterministically, with policy compliance and informed consent.

  • M

    Capability Manifest

    What the service does, what data it needs (input fields), what it produces (output fields), constraints (SLA, fees, availability hours), and redress information (complaint URL, appeal process, ombudsman details). This is the service's public contract.

  • P

    Policy Ruleset

    Eligibility rules expressed as structured conditions, with edge cases and exceptions. The PolicyEvaluator in @als/legibility executes these deterministically — the LLM never decides eligibility.

  • S

    State Model

    A state machine defining the lifecycle of a service interaction: states, transitions with triggers, and terminal conditions. The StateMachine in @als/legibility advances through states as the agent collects data and evaluates policy.

  • C

    Consent Model

    Data grants (what personal data is accessed, by whom, for how long), delegation scope, and revocability rules. The ConsentManager checks these before any data is shared with a service.

Completeness scoring. The service detail page shows a percentage score based on which artefacts are present and how thoroughly they're populated. A yellow gap-analysis box lists exactly which artefacts or fields are missing.

The service editor

Each service can be edited through a structured form with sections for:

Core & Schema

Name, department, description, input/output field definitions with types and descriptions.

Constraints & Redress

SLA, fees, availability, complaint URL, appeal process, ombudsman, escalation phone and hours.

Policy & State

Eligibility rules with conditions, state definitions with transitions, consent grants and delegation scope.

Additionally, the editor includes a Card Definitions section for mapping service states to visual cards displayed in the citizen chat, and an Audit section for data retention period, data controller, and lawful basis.

LLM-assisted generation

For catalogue services that lack artefacts, a Generate button triggers the AnthropicAdapter to scaffold policy, state model, and consent artefacts from the service's basic metadata. Generated artefacts are timestamped and marked as machine-generated for human review.

Gap analysis

The gap analysis view answers a single question for each department: how ready are your services for agent delivery?

Top-level KPIs show 1,653 total services, 113 with full artefacts, 7% coverage, and 1,540 services needing artefacts. The catalogue draws from the full GOV.UK services directory, so the gap is deliberately large — it represents the scale of the challenge, not a failure to deliver.

Department coverage cards

Each department gets a summary card with a colour-coded progress bar showing the ratio of full-artefact services to total services. Services in the gap table are sorted by priority: demo-critical services first (those used in live department demonstrations), then transactional services, then reference material. 6

Evidence explorer

Every agent interaction produces a trace — an append-only sequence of events stored in the @als/evidence package. The evidence explorer lets designers inspect exactly what happened during any citizen session.

Two-panel layout

The left panel lists trace sessions (by ID and timestamp with event counts). Selecting a trace opens its events in the right panel, which offers two tabs:

Explorer tab

Filtered event list with expandable payloads

  • Filter by event type with colour-coded badges
  • Expand any event to inspect the full JSON payload
  • Summary bar shows event count, receipt count, and type breakdown

Replay tab

Chronological event playback

  • Step through events in the order they occurred
  • See the full chain of agent reasoning
  • Useful for debugging service flows and consent sequences

Event types

Traces capture every decision point in the agent pipeline. Each event type is colour-coded for visual scanning:

llm.request capability.invoked policy.evaluated consent.requested consent.granted credential.verified receipt.issued state.transition handoff.requested error
Traceability principle. Every agent action — from the initial LLM request through policy evaluation to consent grants and service completions — is captured as an immutable event. This is the evidential backbone that makes agentic government services auditable.

Service ledger

The ledger tracks citizen cases as they move through services — providing operational metrics for service owners and identifying where citizens get stuck.

Each service has its own ledger dashboard, accessible from the service detail page. The ledger fetches live data from the citizen app's API.

What the ledger shows

Aggregate view

  • Status breakdown bar (completed, active, handed off, rejected)
  • Agent vs human action ratio with visual bar chart
  • Average progress percentage across all cases

  • Paginated case table (20 per page) with status filters
  • Per-case: user ID, current state, progress %, agent/human action counts
  • Click through to case detail with timeline and state flow visualisation
  • Review dialog for human assessment of case handling
Bottleneck detection. The BottleneckChart component identifies states where cases accumulate without progressing. This surfaces design problems in service flows — for example, a consent step that citizens consistently abandon, or a data-collection state that requires information citizens don't have to hand.
8

Personas

Test user identities used to simulate citizen interactions during demos and testing. Each persona has a complete profile with demographic data, employment status, wallet credentials, and department-specific context.

The persona page shows a card grid with department filter tabs (configured via PERSONA_DEPARTMENTS in @als/personal-data). Each card displays the persona's avatar, name, age, location, employment status, income, and credential count.

Personas are editable through a structured form with sections for basic identity, benefits, family composition, health information, data sources, and a raw JSON editor for advanced fields. Changes require a dev server restart to take effect.

Department-scoped personas. Personas are designed for specific department demos — a bereavement persona for HMRC and DWP, an immigration persona for the Home Office, a sentencing persona for MoJ. The department filter ensures designers see only the personas relevant to their demo.

Architecture rule. Legibility Studio does not import @als/evidence directly — doing so causes native module crashes (lru-cache / better-sqlite3 conflicts). All evidence and ledger data is fetched via HTTP from the citizen app API at NEXT_PUBLIC_CITIZEN_API (default http://localhost:3100).
