Service Builder Briefing

Legibility Studio

How policy becomes a service that any AI agent can invoke — and why that matters for accountability.

The Legibility Studio is the service-builder interface for the Agentic Legibility Stack. It transforms policy documents into machine-readable service definitions — manifests, eligibility rules, state machines, and consent models — that sit as infrastructure beneath any agent product. This briefing explains the mechanics, the interface, and why the decoupling between services and agents is necessary.

What the Studio does

The Legibility Studio is the place where service owners design, generate, and monitor government services that AI agents can access on behalf of citizens. It is the control plane — the admin interface — not the citizen-facing product.

Design

Create services

Define a service from scratch — its eligibility rules, data requirements, consent model, and state machine — or generate all four artefacts from a GOV.UK page or uploaded policy document.

Monitor

Operational ledger

Track every citizen case through its state machine in real time. See which cases are active, completed, rejected, or handed off to a human. Spot bottlenecks.

Audit

Evidence plane

Replay any agent interaction event by event. Every LLM call, policy evaluation, consent request, state transition, and receipt is recorded immutably.

The key idea: The Studio does not build agents. It builds the infrastructure that agents consume. Any agent product — a chatbot, a voice assistant, a form-filling service — can sit on top of the same service definitions. The Studio is where those definitions are authored and governed.

The four legibility artefacts

Every service in the stack is defined by exactly four JSON files. Together, they make a service legible — transparent enough for a citizen to understand what is happening, and structured enough for a machine to enforce it.

Artefact 1

Manifest

The service contract. Declares what data the service needs, what it returns, fees, SLA, redress options, and handoff configuration. Think of it as the API specification for a government service.

"id": "dvla.renew-driving-licence",
"name": "Renew a driving licence",
"department": "DVLA",
"input_schema": { full_name, dob, licence_number… },
"constraints": { sla: "3 weeks", fee: "£14" },
"redress": { complaint_url, appeal_process… }
Artefact 2

Policy Ruleset

Machine-readable eligibility rules. Each rule has a condition (field, operator, value), a failure explanation, and optional edge cases for medical conditions or unusual circumstances.

"rules": [
  { field: "age", op: ">=", value: 16,
    reason: "Must be 16+ to hold a licence" },
  { field: "licence_status", op: "!=", "revoked",
    triggers_handoff: true }
]
Artefact 3

State Model

A finite state machine defining the citizen's journey. Each state can trigger a receipt. Transitions are guarded by conditions. Terminal states include completed, rejected, and handed-off.

not-started → identity-verified → eligibility-checked
→ consent-given → details-confirmed
→ payment-made → application-submitted
→ completed | rejected | handed-off
Artefact 4

Consent Model

Explicit data-sharing grants. Each grant names the data shared, its source, purpose, and duration. Includes delegation rules — what the agent can and cannot do on the citizen's behalf.

"grants": [
  { id: "identity-verification",
    data: [name, dob, NI number],
    source: "one-login", duration: "session" }
],
"delegation": { limitations: "Cannot make payment" }
Why four artefacts, not one? Because legibility requires separation of concerns. The manifest tells citizens what the service does. The policy tells them whether they qualify. The state model tells them where they are. The consent model tells them what data is being shared. Each can be audited, versioned, and governed independently.

How a service gets created

There are two paths: manual authoring through the Studio's form interface, or LLM-assisted generation from a GOV.UK page (and in future, an uploaded policy document).

Path 1: LLM-assisted generation

The current system scrapes the GOV.UK guidance page for a service, enriches it with CDDO metadata (login requirements, data collected, eligibility complexity), and feeds both to Claude Sonnet with a structured prompt and few-shot examples. The LLM generates all three missing artefacts — policy, state model, and consent — which are then validated and stored.

  1. Source content

    The Studio fetches the GOV.UK guidance page and extracts structured content — sections, headings, eligibility criteria. CDDO enrichment data adds metadata about login requirements and data collected.

  2. Classify typology

    The service is classified into one of 8 typologies (Benefit, Obligation, Registration, etc.) which selects a state-model template as the starting point.

  3. Generate artefacts

    Claude Sonnet receives a system prompt with JSON schemas, few-shot examples, and the service's GOV.UK content. It produces three labeled JSON blocks: policy, state-model, consent.

  4. Validate & store

    Each artefact is validated against its schema — policy operators are normalised, state models are checked for valid transitions, consent grants are verified. Valid artefacts are persisted to the service store.

Path 2: Manual authoring

The Studio provides a full form editor for each artefact. A service designer can build a service from scratch, defining every rule, state, and consent grant directly.

Service States Panel

Every service has a state machine that defines the citizen's journey. The Studio visualises this as a horizontal flow. Completed states are green, the current state is highlighted in blue, and pending states are grey. This same state flow appears in the operational ledger for each individual case.

How state models work

A state model defines the valid paths through a service. Every service starts at not-started and ends at one of three terminal states: completed (success), rejected (ineligible), or handed-off (escalated to human).

Transitions are guarded — the system only allows moves that are defined in the model. This makes the agent's behaviour deterministic at the service layer, even though the language layer is probabilistic. The agent cannot skip steps, cannot move backwards, and cannot reach a state without satisfying the transition conditions.

States marked with receipt: true automatically generate a citizen-facing receipt when entered — proof of what happened at that point in the journey.

Persona Management

The Personas section manages test citizens used for simulation. Each persona has structured identity data (name, DOB, NI number, employment status, income, savings), address, communication style preferences (tone, tech-savviness, reassurance needs), credentials, family details, health information, and more. Personas can be AI-generated from a scenario description or hand-crafted through the form editor.

Why personas matter: Service definitions are tested by running simulated citizen journeys against them. A persona with edge-case attributes (over 70, medical condition, non-UK address) will exercise different branches of the policy ruleset and state model than a standard applicant.

Architecture: the decoupled stack

The most important design decision in the stack is the separation between service infrastructure and agent products. The Studio builds the infrastructure. Agent products consume it.

Agent Products — Swappable
Citizen App (chatbot, voice, form)
Any front-end that speaks to citizens. Can be a conversational agent, a traditional web form, a voice assistant, or a mobile app. Multiple products can consume the same services simultaneously.
Orchestration Layer
Orchestrator + LLM Adapter
Deterministic state machine that loads artefacts, evaluates policy, manages state transitions, and only delegates language generation to the LLM. The agent proposes; the orchestrator disposes.
Service Infrastructure — Stable
Legibility Artefacts (Manifest + Policy + State Model + Consent)
Machine-readable service definitions authored in the Legibility Studio. Versioned, validated, and governed independently of any agent. This is the layer that ensures legibility regardless of which product sits above it.
Evidence Layer
Immutable Trace Store + Receipts
Append-only audit trail. Every decision, every data access, every state transition is recorded. Citizen-facing receipts are generated automatically at key states.

Why decoupling matters

Without decoupling, every AI agent product becomes a vertically integrated silo. Each chatbot implements its own eligibility logic, its own state tracking, its own consent model. The rules diverge. Auditability becomes impossible. When policy changes, every product must be updated independently.

With the decoupled stack, service definitions are infrastructure. They are authored once in the Studio, versioned, and consumed by any agent product through a standard interface. When policy changes, the artefact is updated in one place and every product inherits the change immediately.

This is the same principle as separating data from presentation, or separating policy from implementation. The service is not the chatbot. The service is the rules, the journey, the consent model, and the audit trail. The chatbot is just one way to access it.

The Capability Invoker

Every service call — from any agent, through any channel — routes through a single choke point called the CapabilityInvoker. This enforces:

Receipt generation Every invocation produces a citizen receipt
Trace emission Every call is logged to the immutable trace store
Policy enforcement Eligibility is evaluated deterministically, not by the LLM
No bypasses There is no alternative path. Every agent goes through the same gate.

Service typologies

Every service is classified into one of eight typologies. Each typology comes with a default state-model template that the generation pipeline customises for the specific service.

Business grants, research funding. Application + assessment cycle.
