Service Typologies & the ALS Platform

How eight service typologies shape the platform today, where the model falls short, and concrete proposals for deeper integration.

Prepared for the service typologies team. This briefing maps exactly where the typologies operate within the Agentic Legibility Stack, where their influence stops, and proposes eight ways to deepen their value.

Executive summary: The ALS platform already uses the eight service typologies as a foundational organising principle. Each of 108 services is tagged with a typology that flows through a type-inference pipeline selecting a state machine template, UI card definitions, and LLM instructions. However, much of the typology nuance is lost in the middle — eight service types currently collapse to just four distinct interaction patterns. This briefing maps the current integration, highlights what works well, and proposes eight concrete extensions.

How typologies flow through the platform

When a citizen begins a service journey, the platform resolves their experience through a five-stage pipeline. The service typology enters at the top and influences every downstream decision.

1
Service Graph
Each of 108 services tagged with a serviceType from the 8 typologies. Defined in graph-data.ts.
2
Type Inference
inferInteractionType() maps each typology to an interaction type. This is where nuance narrows.
3
State Machine Template
Interaction type selects a full state machine: states, transitions, auto-transitions, terminal configs.
4
Card Resolution
(interactionType + currentState) → UI cards. Three-level cascade: DB overrides → static → template.
5
LLM Instructions
State-specific prompts guide the AI agent's tone, pace, data handling, and transition triggers.

The mapping bottleneck

At step 2, eight service typologies collapse into just four interaction patterns. Four typologies share a single application template:

Service typology Interaction type Notes
benefit entitlement grant → application 3 types share one pattern
legal_process → application Falls through to default
obligation → payment_service Distinct pattern
registration → register Distinct pattern
document → license Distinct pattern
Key finding: The remaining four interaction types — portal, informational_hub, appointment_booker, task_list — exist as templates but are not currently mapped from any of the eight typologies. They are available for use if the typology model expands.

What this shows: The same chat interface, same card components, same consent flow — but the typology determines which cards appear, how many steps there are, and what data is collected. The application pattern has document upload + assessment. The payment_service skips straight to calculate + pay. The register is the simplest: one form, done. The license combines documents AND payment — the most complex path.

What works well today

The current typology integration delivers significant architectural value, particularly for scaling from hand-crafted prototypes to the full 108-service catalogue.

  • 108 services run "on rails" without hand-crafting. A single typology tag generates a complete state machine, card set, and instruction template for any service.
  • Three-level override system. Templates provide the baseline, the static registry handles bespoke services (Universal Credit, driving licence), and Studio DB overrides allow per-service customisation without code changes.
  • Type determines both journey shape and UI. The typology doesn't just influence the state machine — it directly controls which forms, uploads, and payment flows appear at each step.
  • Consent and data pre-fill are type-aware. Cards auto-fill from verified (Tier 1) and submitted (Tier 2) personal data, with read-only locking on verified fields.
  • Terminal states have type-appropriate receipts. Completed, rejected, and handed-off outcomes produce distinct receipt cards with contextual next steps and related service suggestions.

Where typologies could add more value

The typology model is well-established at the edges (service graph & UI) but much of its nuance is lost in the middle. Here are eight concrete proposals for deeper integration.

Proposal A High impact

Resolve the collapse in the middle

Four of eight typologies — benefit, entitlement, grant, and legal_process — collapse into a single application interaction type. A probate application and a Universal Credit claim get identical journey structures, flattening meaningful differences in complexity, user anxiety, and legal weight.

Proposal: Create dedicated interaction types for at least benefit, entitlement, and legal_process. A benefit journey should include income assessment and payment scheduling. An entitlement should include employer verification. A legal process should include witness/attestation steps and solicitor routing.
Proposal B High impact

Type-specific terminal flows

A payment service should always end with a payment card. A registration should produce a confirmation certificate. Currently terminal states are generic — the same "completed" configuration regardless of typology.

Proposal: Define type-specific "exit patterns" that guarantee typology-appropriate final steps. An obligation always includes PAYMENT_CARD. A registration always produces a CERTIFICATE_CARD. A benefit always ends with a PAYMENT_SCHEDULE_CARD showing expected payment dates.
Proposal C High impact

Type-specific consent language

An obligation ("you must provide this information") has fundamentally different consent framing than a benefit ("you may be entitled to support"). Currently consent language is generic and doesn't reflect whether the citizen is exercising a right, fulfilling a duty, or requesting support.

Proposal: Template consent language per typology. Benefits: supportive framing ("To check what you're entitled to..."). Obligations: directive framing ("You are required to..."). Registrations: factual framing ("To record this event..."). This shapes how the AI agent introduces data-sharing requests.
Proposal D Medium impact

Type-specific escalation paths

A legal process should escalate to legal advice. A benefit should route to a DWP caseworker. Currently handoff is one-size-fits-all: the agent flags "needs human intervention" without type-aware routing.

Proposal: Define escalation targets per typology. Legal processes → Citizens Advice or solicitors. Benefits → departmental caseworkers. Obligations → HMRC or DVLA helplines. This metadata is already partially available from the service graph's department field.
Proposal E Medium impact

Type-aware proactivity rules

Benefits should be proactively surfaced ("Based on your records, you may be eligible for..."). Obligations should trigger warnings ("Your MOT expires in 3 weeks"). The proactive flag exists per service but there are no default rules by typology.

Proposal: Default proactivity patterns per typology. Benefits/entitlements: eligibility-based nudges. Obligations: deadline-based warnings. Documents: expiry-based reminders. Registrations: life-event-triggered prompts.
Proposal F Medium impact

Typology dashboard in Legibility Studio

Studio currently shows services as a flat list. There's no way to see coverage, completeness, or journey quality at the typology level.

Proposal: Add a typology-level view to Studio showing: services per type, template completeness (states/cards defined), override coverage, and journey analytics grouped by typology. This makes the typology model a first-class management concept.
Proposal G Refinement

Type-specific canonical data schemas

Each typology has characteristic data needs. Benefits need income and housing. Registrations need event details. Obligations need deadline dates. Currently card fields are defined per-service or per-template, with no typology-level schema.

Proposal: Define canonical data field sets per typology that auto-populate template cards. A new benefit automatically includes income and housing fields. A new registration includes event details. This reduces onboarding work and ensures consistency within a typology.
Proposal H Refinement

Typology as a policy primitive

Policy rules are currently defined per-service. Common patterns like "all benefits require income verification" must be repeated in every policy file.

Proposal: Allow policy rules at the typology level, inherited by all services of that type. Service-specific policies extend or override the base. This ensures core requirements (like income checks for benefits) can't be accidentally omitted from new services.

Recommended sequence

A first (unlocks B–H), then B + C, then the medium-impact proposals.

Bottom line: The typologies are already wired into the platform as a foundational organising principle. The single highest-leverage change is resolving the 8→4 collapse at the type inference layer (Proposal A). Once each typology has a dedicated interaction pattern, every downstream system — state machines, cards, LLM instructions, consent, escalation — can express genuinely typology-specific behaviour.
