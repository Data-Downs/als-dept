Critical Review — March 2026

Is the Stack Actually Agentic?

The platform infrastructure is more capable than the agent that sits on top of it.

The Agentic Legibility Stack already has cross-service reasoning infrastructure — a typed service graph with 108 services, 16 life events, topological planning, and persona-aware filtering. But the LLM agent doesn't yet leverage it within conversations. Four interaction models show what becomes possible when it does.

The Honest Assessment

What's Built vs What the Agent Uses

The platform has two layers: a rich cross-service infrastructure (service graph, life event plans, persona-aware filtering) and an LLM agent layer. Currently, the agent's role is limited to three things: generate conversational wrapper text around deterministic decisions, extract facts from citizen input into structured fields, and propose state transitions that the state machine validates. The infrastructure is ready — the agent just isn't wired into it yet.

Citizen selects service → LLM narrates form → Citizen fills form → Engine decides → LLM narrates result

Within a single service, everything that matters — eligibility, consent, state advancement, card selection — is pre-authored and deterministic.

What's built and working

  • Full auditability — every decision is traced
  • Safety — LLM cannot override policy
  • Reproducibility — same input, same output
  • Two-tier data model — verified credentials vs incidental data
  • Granular consent — properly authored per service
  • Service graph — 108 services, typed REQUIRES/ENABLES edges
  • Life event plans — 16 life events with topological ordering
  • Persona-aware filtering — plans adapt to eligibility
  • Cross-session plan tracking — progress persists across visits

What the agent doesn't yet do

  • Agent is single-service — chat processes one service at a time, despite the graph infrastructure
  • No in-conversation cross-service reasoning — the LLM doesn't query the service graph or suggest next steps
  • No predictive error prevention — collect first, reject after
  • No data minimisation reasoning — everyone gets the same form
  • Confidence unused — fact-extraction confidence is logged but never acted on

The gap

The platform has sophisticated cross-service infrastructure: a dependency graph with topological planning, persona-aware life event decomposition, and multi-session state tracking. But the LLM agent doesn't use any of it. Within a chat conversation, the agent processes one service at a time. The cross-service intelligence lives in the UI layer (dashboard, plan view) rather than in the agent's reasoning loop. The infrastructure is ready — the next step is wiring the agent into it.

Model 1

The Proactive Advocate

The platform already has a service graph with cross-service edges and life event entry points. The Proactive Advocate wires the LLM agent into this infrastructure — the agent queries the graph in real-time, reasons about gotchas, and builds plans within the conversation. Deterministic engines still handle each individual service.

LLM reasons about

Cross-service dependencies

Which services are triggered by the life event, what order to do them in, and what the gotchas are

Stays deterministic

Each service transaction

Eligibility, fees, identity verification, consent, document validation

Key insight

Infrastructure exists, agent doesn't use it

The service graph and life event plans are built. The gap is connecting the LLM to them so it can reason about gotchas and sequencing in real-time.

Model 2 — Recommended

The Contextual Error Preventer

Instead of collect-then-validate, the agent reasons about each piece of information as it arrives — catching problems before they become formal rejections.

LLM reasons about

Likely outcomes

Predictive validation, contextual interpretation of answers, soft pre-screening before entering the deterministic flow

Stays deterministic

Formal decisions

The actual eligibility decision, formal validation, acceptance or rejection

Key insight

Breaks the rejection loop

"Fill form → get rejected → try again" becomes "agent warns you → you fix it first → apply once"

Model 3 — Recommended

The Data Minimiser

Instead of showing everyone the same 23-question form, the agent reasons about which fields this citizen actually needs to provide, based on their specific situation.

LLM reasons about

Contextual relevance

Conditional field reasoning, data reuse from previous services, minimum viable disclosure

Stays deterministic

Legal requirements

Which fields are legally mandatory, data validation, consent

Key insight

Forms can't reason

Government forms ask everyone everything because forms can't reason about who needs what. An agent can.

Model 4

The Life-Event Coordinator

Citizens don't think in services, they think in life events. The platform already supports this — 16 life events with topological plans, persona-aware filtering, and cross-session plan tracking in the UI. This model moves that coordination into the agent itself, so it can actively guide citizens across services within the conversation.

LLM reasons about

Life event decomposition

Breaking events into service sequences, cross-service state tracking, sequencing intelligence, interruption/resume

Stays deterministic

Each service's processing

Consent per service, data sharing, individual service transactions

Key insight

From UI to agent

The plan view and dashboard already show multi-service journeys with progress tracking. The next step is the agent actively guiding citizens through them, not just the UI.

The Shift

Connecting the Agent to What's Already Built

The architecture's separation of concerns is correct, and significant cross-service infrastructure already exists. The change needed is not in building new data models — it's in wiring the LLM agent into the infrastructure that's already there, and extending it where gaps remain.

Current: agent handles one service, platform shows the map

Dashboard shows life event plan → Citizen selects one service → LLM narrates form → Engine decides → Citizen returns to dashboard for next service

Proposed: agent reasons across services using existing graph

Citizen describes situation → LLM reasons about services, sequencing, issues → LLM proposes plan → Citizen agrees → Deterministic engine per service → LLM tracks, catches issues, adapts

The LLM should reason in spaces where determinism is impossible

Where the LLM adds value

Reasoning spaces

  • ★ Combinatorial spaces — life events × services × circumstances
  • ★ Predictive reasoning — anticipating rejections before they happen
  • ★ Contextual relevance — which of 23 fields matter for this person
  • ★ Cross-service coordination — no single engine sees the full landscape
  • ★ Temporal reasoning — "do X before Y because Z"
Where the LLM must never act

Deterministic invariants

  • ✗ Make eligibility decisions
  • ✗ Override consent requirements
  • ✗ Modify application data
  • ✗ Suppress mandatory information
  • ✗ Skip or re-order mandatory steps

Recommended Next Step

Build the Agentic Layer

The platform infrastructure is substantially complete. The next step is building a genuinely agentic application on top of it — one where the LLM agent actively uses the service graph, life event plans, and persona context to guide citizens through multi-service journeys.

Infrastructure ready

Models 1 & 4: Cross-Service Agent

The service graph, life event plans, persona filtering, and plan tracking are already built. The Proactive Advocate and Life-Event Coordinator primarily need the agent to be connected to this infrastructure via MCP tools or function calls. This is the highest-leverage work: turn existing data into active agent reasoning.

Prototype with: A life event conversation (e.g. "turning 70") where the agent queries the service graph, identifies related services, and builds a plan — within the chat.

New capability needed

Models 2 & 3: Predictive & Adaptive

The Error Preventer and Data Minimiser require new infrastructure — a soft pre-screening protocol and a field relevance engine. These add genuine new reasoning capabilities but work within the existing single-service flow.

Prototype with: Driving licence renewal — medical condition pre-screening (Model 2) and field reduction for straightforward cases (Model 3).

The bottom line: This is no longer a question of building infrastructure — the service graph, life event plans, and cross-session state tracking already exist. The question is whether to build a new agentic application that wires the LLM into this infrastructure, giving it something genuinely meaningful to reason about: which services, in what order, and whether this citizen should even be filling out a form right now. The deterministic layer is sound. The platform is ready. The agent needs to catch up.
