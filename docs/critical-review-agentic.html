Critical Review — March 2026

Is the Stack Actually Agentic?

The architecture's separation of concerns is sound. But the LLM is in the wrong cage.

An honest assessment of whether the Agentic Legibility Stack genuinely leverages agentic capabilities — or is replicating forms with better UX. Four alternative interaction models are presented, each illustrated as a conversation prototype using the driving licence renewal service.

The Honest Assessment

What the LLM Actually Does Today

Currently, Claude's role in the stack is essentially three things: generate conversational wrapper text around deterministic decisions, extract facts from citizen input into structured fields, and propose state transitions that the state machine validates.

Citizen selects service → LLM narrates form → Citizen fills form → Engine decides → LLM narrates result

Everything that matters — eligibility, consent, state advancement, card selection, field requirements — is pre-authored and deterministic.

What's genuinely good

  • Full auditability — every decision is traced
  • Safety — LLM cannot override policy
  • Reproducibility — same input, same output
  • Two-tier data model — verified credentials vs incidental data
  • Granular consent — properly authored per service

What's missing

  • No autonomous goal decomposition — journeys are pre-authored state machines
  • No cross-service reasoning — each service is an isolated linear flow
  • No predictive error prevention — collect first, reject after
  • No data minimisation reasoning — everyone gets the same form
  • Confidence unused — fact-extraction confidence is logged but never acted on

The verdict

The result is a sophisticated form-filling system with conversational UX. The citizen fills in the same fields they'd fill in on a GOV.UK form — they just do it via cards injected into a chat flow instead of pages on a website. The LLM's reasoning capabilities are wasted on text generation.

Model 1

The Proactive Advocate

Citizen describes a life situation. The agent reasons across multiple services, identifies what's relevant, warns about gotchas, and builds a plan. Deterministic engines handle each individual service.

LLM reasons about

Cross-service dependencies

Which services are triggered by the life event, what order to do them in, and what the gotchas are

Stays deterministic

Each service transaction

Eligibility, fees, identity verification, consent, document validation

Key insight

Combinatorial space

Life events × services × circumstances is too large for state machines. This is where LLM reasoning shines.

Model 2 — Recommended

The Contextual Error Preventer

Instead of collect-then-validate, the agent reasons about each piece of information as it arrives — catching problems before they become formal rejections.

LLM reasons about

Likely outcomes

Predictive validation, contextual interpretation of answers, soft pre-screening before entering the deterministic flow

Stays deterministic

Formal decisions

The actual eligibility decision, formal validation, acceptance or rejection

Key insight

Breaks the rejection loop

"Fill form → get rejected → try again" becomes "agent warns you → you fix it first → apply once"

Model 3 — Recommended

The Data Minimiser

Instead of showing everyone the same 23-question form, the agent reasons about which fields this citizen actually needs to provide, based on their specific situation.

LLM reasons about

Contextual relevance

Conditional field reasoning, data reuse from previous services, minimum viable disclosure

Stays deterministic

Legal requirements

Which fields are legally mandatory, data validation, consent

Key insight

Forms can't reason

Government forms ask everyone everything because forms can't reason about who needs what. An agent can.

Model 4

The Life-Event Coordinator

Citizens don't think in services, they think in life events. "I'm retiring." "I'm having a baby." "Someone died." Each event spans multiple services with complex interdependencies. The agent coordinates across sessions.

LLM reasons about

Life event decomposition

Breaking events into service sequences, cross-service state tracking, sequencing intelligence, interruption/resume

Stays deterministic

Each service's processing

Consent per service, data sharing, individual service transactions

Key insight

Multi-session state

A citizen "moving abroad" would navigate 6-8 separate services themselves. The coordinator does this for them across multiple sessions.

The Shift

Where the LLM Should Reason

The current architecture's separation of concerns is correct. The change needed is not in the deterministic layer. It's in what the LLM is asked to reason about.

Current flow

Citizen selects service → LLM narrates form → Citizen fills form → Engine decides → LLM narrates result

Proposed flow

Citizen describes situation → LLM reasons about services, sequencing, issues → LLM proposes plan → Citizen agrees → Deterministic engine per service → LLM tracks, catches issues, adapts

The LLM should reason in spaces where determinism is impossible

Where the LLM adds value

Reasoning spaces

  • ★ Combinatorial spaces — life events × services × circumstances
  • ★ Predictive reasoning — anticipating rejections before they happen
  • ★ Contextual relevance — which of 23 fields matter for this person
  • ★ Cross-service coordination — no single engine sees the full landscape
  • ★ Temporal reasoning — "do X before Y because Z"
Where the LLM must never act

Deterministic invariants

  • ✗ Make eligibility decisions
  • ✗ Override consent requirements
  • ✗ Modify application data
  • ✗ Suppress mandatory information
  • ✗ Skip or re-order mandatory steps

What would need to change

ComponentPackagePurpose
Service catalogue for LLM reasoning @als/runtime Structured metadata about every service: criteria, timelines, common rejection reasons, dependencies. The LLM reasons over this; it doesn't replace the policy engine.
Soft pre-screening protocol @als/legibility Read-only access to policy rules so the agent can ask "would this citizen likely qualify?" without creating a formal application.
Cross-service dependency graph @als/runtime Which services depend on which, ordering constraints, what can run in parallel.
Multi-session state persistence @als/runtime Track progress across services and sessions for life-event coordination.
Agent reasoning audit trail @als/evidence Every suggestion the agent makes is logged with reasoning, so "the system told me to do X" has a verifiable record.
Field relevance engine @als/legibility Maps citizen context to required vs optional fields, enabling the data minimisation model.
Recommended Next Step

Start with Models 2 and 3

The Error Preventer and Data Minimiser deliver the most citizen-facing value with the least architectural disruption. Both work within the existing single-service flow but change how the LLM engages within it.

Low disruption, high impact

Model 2: Error Preventer

Works within the current single-service flow. Add a "soft pre-screening" step before the formal card is presented. The LLM asks 1-2 conversational questions to catch likely problems. No new infrastructure needed — just policy metadata the LLM can reason about.

Prototype with: Driving licence renewal for citizens with medical conditions.

Low disruption, high impact

Model 3: Data Minimiser

Works within the current card system. Add a field-relevance layer that maps citizen context to required vs optional fields. The card renders with fewer fields; a "show all fields" toggle preserves the full form.

Prototype with: Driving licence renewal for a straightforward case (no conditions, unchanged details).

Larger build

Model 1: Proactive Advocate

Requires cross-service reasoning infrastructure and a service catalogue with gotcha metadata. Build after Models 2-3 prove the pattern of LLM reasoning alongside deterministic control.

Largest build

Model 4: Life-Event Coordinator

Requires multi-session state persistence and cross-service dependency graphs. The most ambitious model — but also the most transformative for citizens navigating complex life events.

The bottom line: The separation of concerns in the current architecture is correct and should be preserved. The opportunity is not in changing the deterministic layer — it's in giving the LLM something meaningful to reason about. Right now, the most capable reasoning model in the world is being used to write paragraphs around forms. It should be reasoning about which forms, in what order, and whether this citizen should even be filling one out right now.
